# V1: the smallest transformative whole

**Status:** proposed delivery specification synthesized from the founding collaboration. This is a finish line, not a report of completed work. Stable scenario IDs let agents and tests refer to it without copying the entire vision.

## The product judgment

The most valuable first product is **a reflective Codex workbench for recovering, composing, delegating, and improving substantial ongoing work**. The existing trace/UI path and the Eidos process/authority path should meet here. Do not choose a new abstract demo just because it is easier to finish than that integration.

The first owner is a technically sophisticated person doing long-running intellectual and engineering work with agents. They already have native Codex, accumulated conversation history, many partially understood artifacts, and a strong preference for direct manipulation over administrative dashboards. They need their work and its context to survive model/session boundaries.

The minimum is transformative when the owner can reliably do something they would otherwise manage by laborious scrolling, copying, retelling, terminal juggling, and unauditable experimentation. It need not implement a distributed operating system, a complete proof language, or every possible renderer.

## One complete use case

Return to an old, complicated design task. Open a saved workspace containing a native conversation and a relevant older experiment. Find the decision and its evidence, including a rejected alternative. Select relevant regions from both, preview a context packet, and delegate a bounded question to a specialist. The specialist may ask for additional evidence; the user can inspect the question and choose what to disclose. Pending work survives a reload or runner interruption. The returned artifact cites its actual inputs and supports a meaningful comparison. Adopt a selected result or patch, leaving the baseline and rejected alternative intact. Propose a tested improvement to the context builder or lens that would make this workflow better next time.

This is one coherent loop. Each subsystem must contribute to it.

## Required capabilities

### Durable project memory, not just transcript storage

Import native history and record new work with stable evidence references. Produce versioned navigational interpretations, preserve noncontiguous support, and return to raw evidence. Handle incomplete histories honestly. A useful semantic tree is not allowed to replace the transcript.

### Context as a reviewable object

A person can see what evidence, instructions, skills/tool descriptions, and configuration a new task is intended to receive. Supported capture distinguishes that projection from actual observed native input. Changes have immutable versions and useful diffs. An old task retains the context that was actually selected for it.

### More than one view, one underlying world

Provide an arrangement with linked semantic, evidence, work, and comparison apertures. Expose the current selection and allow at least one meaningful agent-assisted rearrangement or context selection as a reviewable operation. Persist the arrangement and provenance. Do not spend V1 on a general-purpose layout marketplace.

### Real bounded delegation

Use the native Codex subscription-backed path for useful specialist work where available. Record context, restrictions, workspace isolation, and costs. Eidos process state must represent pending questions and received results, not wrap a long blocking function while claiming asynchronous continuity. A second synthetic runner alone is not this capability.

### Safe alternatives and reintegration

Support a named reinterpretation or isolated native/mock branch, a baseline comparison, and an explicit adoption decision. Keep workspace effects separate from conversation history. A result can be brought back as a grounded artifact without importing every child message or inheriting unintended live authority.

### Recovery and self-inspection

Resume the overall investigation, not only an inner micro-protocol. The workbench should expose its own context construction, native operations, lens/model revisions, and pending continuations. Its first improvement experiment should use this evidence and yield a reversible change.

## Acceptance scenarios

| ID | Demonstration and required evidence |
| --- | --- |
| V1-01 | **Reorientation:** load a genuinely long native history or a representative sanitized fixture, recover a decision, rationale, source support, and open question without full linear rereading. Record task completion and navigation path; do not assert speed without measurement. |
| V1-02 | **Evidence integrity:** every generated durable claim/episode has resolvable support or is explicitly labelled unsupported/hypothetical. Unknown raw fields survive import, normalization, and subsequent re-indexing. |
| V1-03 | **Two-aperture coherence:** selecting a semantic item reveals its actual source ranges; changing layout or reloading retains object identity and useful focus. A patch/output/pending question has a native rendering, not only JSON. |
| V1-04 | **Context preview:** select disjoint evidence from two threads, build a named context packet, inspect included/excluded ingredients and provenance, revise it, and compare versions before delegation. |
| V1-05 | **Joint bounded investigation:** an actual specialist works from the selected packet, returns an attributable artifact, and cannot gain additional world authority by naming another Cut or executor. Demonstrate what was supplied and what was observed. |
| V1-06 | **Pending interaction:** the specialist requests evidence through a visible inquiry. Offer, refusal, and deferral are distinct; pending does not consume the waiting continuation or duplicate the source decision. |
| V1-07 | **End-to-end restart:** interrupt after request, after external response, after local commit, and before outer reintegration. Resume the same investigation identity; no silently duplicated accepted result or claimed exactly-once external effect. Unknown outcomes remain visible. |
| V1-08 | **Alternative without contamination:** reinterpret or fork from a named baseline under different context/lens settings. Isolate file/external effects as required. Compare and adopt a selected result without modifying source history or reviving historical authority. |
| V1-09 | **Context lineage:** change a supported instruction/skill/context ingredient, record the new version and activation boundary, and identify affected requests at the finest captured granularity. Missing provider visibility must be explicit, not fabricated. |
| V1-10 | **Reflective composition:** a person or agent proposes a useful arrangement/aperture change through semantic targets. The user can inspect, apply, and undo it; the resulting composition is recorded. |
| V1-11 | **One evidence-based improvement:** propose a context/lens/workflow patch from observed friction, compare baseline and changed behavior on stated cases, review regressions/cost, then adopt or reject with provenance and rollback. |
| V1-12 | **Boundary review:** demonstrate guessed-name rejection at exposed boundaries, protected successor admission, private trace handling, supported native ownership, and bounded/cancellable work. An internal trusted API must not accidentally become remotely callable authority. |

These are acceptance contracts, not a claim that every action is a new Eidos primitive. Use current modules and the smallest adapters that preserve the distinctions.

## Delivery sequence

**Cycle A — connect the halves.** Establish stable references from trace evidence into one semantic selection/context packet and into a real bounded task. Surface its output, provenance, and basic pending/restart state in the existing UI. Integrate continuously; do not let UI and runtime lanes invent incompatible object identities.

**Cycle B — make it trustworthy to use.** Close outer-attempt recovery and admission boundaries, improve large-history navigation, context versioning, comparison, and native capability reporting. Exercise failure injection and real workflows, not only happy-path fixtures.

**Cycle C — use it to improve itself.** Deliver one complete reflective edit/evaluation/adoption cycle, with saved arrangements and alternate interpretations. Use observed user friction to choose the next generalization.

These are dependency stages, not calendar promises. A feature may progress earlier if its contract is independent. An acceptance claim needs an artifact and a reproducible check.

## The next session's first integrated target

Choose one realistic two-thread question. Produce a persisted **Investigation** convention with source selections, context revision, native worker references, pending/result state, and an explicit adoption record. The name is provisional; the obligation is durable end-to-end identity. Build the thin UI path and the runtime mapping together. The generic ProcessRuntime should help continue the task across a question, not become an unrelated model-only demo.

Before dispatching implementation agents, agree the minimal cross-lane envelope for evidence, context, task/attempt, artifact, and action precondition. Do not standardize all future ontology. [WORKSTREAMS](WORKSTREAMS.md) provides ownership and tests.

## Release gates

**Truth gate:** all claims of observation/coverage and implementation status have evidence. All native feature probes and test results record version/revision.

**Authority gate:** only admitted callers reach authority-changing paths. Legitimate successor outputs are constrained above or within the privileged substrate. Data inspection cannot become arbitrary effect authority.

**Recovery gate:** the outer task as well as inner processes can stop and resume; missing/unknown external outcomes are explicit. No fixture shortcut mutates real work.

**Experience gate:** the owner performs the complete workflow in the actual UI. Navigation, focus, artifact rendering, and context review are useful under realistic size. Build success alone is insufficient.

**Improvement gate:** one evaluated change makes this workflow materially better or identifies a grounded reason to reject the change. Self-modification without evaluation does not pass.

## Explicit non-goals for this release

A replacement Codex harness; a universal type/proof system; a compulsory Flix rewrite; distributed consensus or blockchain; an all-device semantic DNS network; arbitrary native stack migration; a full desktop/window manager; a broad plugin store; many decorative dashboards; unattended instruction self-rewriting; or a promise of exact provider internals without a capture path.

Keep those long-horizon ideas addressable in [DECISIONS](DECISIONS.md). Deferring them does not shrink the aspiration; it protects the first experience that can sustain it.
